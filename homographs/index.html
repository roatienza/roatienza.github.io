One homograph fix, two models

The reading is decided once, by grammar. The spelling is measured per model. Every number below was rendered through the route that serves, not by a harness.

Updated 2026-10-31. Three things on this page changed and one of them changed the 4B's headline. The 4B that serves is accent1, so the table shown is tts4b_fs8_accent1_20261030; the previous version of this page described pronrft2, a checkpoint no request can reach. The 67M numbers now come from POST /v1/audio/speech with TTS_CKPT pinned to Cs2rft1d, because production had been serving Cs2rft1b while every Cs2 render in the repo was made on Cs2rft1d. And the 4B now has a streaming column, which is not a copy of its /tts column.

The three runs are separate measurements: the two 4B routes do not share a baseline and must not be added together.

A row the rule does not rewrite is handed to the engine as the same string with the same seed, so any difference would be the box, not the feature. Every one of them came back with the same md5 — hashed twice, once by the scorer and once independently. The last column is the control for that claim: on the 67M and on the 4B's /tts route every fired row changed, so “identical” above means “left alone”, not “nothing ever changes here”.

On /stream the 4B changed only 13 of its 29 fired rows, and the 16 that did not are all rows the lab engine had already made right: it applies its own homograph cue to the text before synthesising, so on those rows our rewrite and the lab's land on the same reading and the audio is byte-identical. The 13 that changed went 5 → 13 right, so the +8 on that route is the residue the lab's cue misses. That is also the honest reading of the route: on /stream the feature is partly redundant with the engine it calls, and the 16 rows are not evidence of the rule working — they are evidence of it agreeing.

What it does to the voice, on the rows it touches

A rewrite that fixes the word but flattens the delivery is not a fix. The control that can size this is the spread of a different draw of the same sentence (seeds 0, 1000, 2000) — the variation a listener already accepts between two renders. If the rule's movement sits inside that, it is not distinguishable from the model's own noise.

On every feature but duration the rule moves less than a different draw of the same sentence, on both models. Duration is the one real effect and it is not noise: the seed never changes length (0.000 on all 73 rows) while the rule adds +0.08 s, which is the carrier being a longer word than the one it replaces. A same-text, same-seed repeat control was also run and is width zero (0.000 on 25/25 and 15/15 rows): it proves the box is deterministic and cannot size an effect, so it is not used here to claim one.

This is a measurement of prosodic features, not a naturalness rating. Nobody has yet judged whether a carrier sounds like a person; every carrier on this page is validated as “the phones match”, never as “this sounds right”.

What the fix changed in real corpus text

The corpus check reads 4,494,335 rows across four manifests (v2, base, emilia, yodas). Before the fix, on the 974 688 rows measured on 2026-10-29, 26.9 % of Cs2's rewrites and 21.2 % of the 4B's had no cue in range — the frequency fallback chose the reading. After the fix that share is 0: an occurrence the table cannot decide is left as written.

Two held-out manifests, 11 902 real sentences. The rule changes 0.2 % of them and never touches markup. The rewrite is a few tens of microseconds against a render of seconds, and the table load is a one-off at import. Those are counts of how often the feature acts; they are not a measured improvement in comprehension, which nobody has tested.

Where the code runs

The feature is seven files in two trees, plus two generated carrier tables. Six of them are on onit/homographs; the hook that calls them is not.

pathwhat it doessource of truth
corpus/text/homographs.pythe reading table and the grammar cues in git
corpus/text/homograph_core.pyresolve(): which reading this occurrence needs in git
corpus/text/homograph_apply.pyplan(): which spelling THIS model needs in git
corpus/text/carriers/&lt;model&gt;.jsonthe measured decisions, one file per checkpoint in git
serving/tts/textnorm.py+35 lines: call the applier last, after textnorm in git
corpus/text/normalize_en.py+43 lines: the same call on the training path in git
serving/tts/server.pythe hook itself: _apply_homographs at parse() on the box only

A table is keyed by model_id, and three things are checked before a single rewrite is applied, each failing closed to “speak the text as written”: the table's rule_version against the code's, its engine against the engine actually serving (run_server.sh defaults TTS_ENGINE=4b, so the 67M API answers through the 4B lab engine unless that is emptied — a Cs2 table there would describe a voice the box is not using), and its checkpoint_sha256 against the checkpoint on disk. The last one exists because on 2026-10-30 the systemd drop-in was repointed from accent1 to accent2 while TTS_HOMOGRAPH_MODEL still said accent1; both files are 13 224 509 793 bytes and both load.

Deploy note. serving/tts/deploy.sh rsyncs serving/tts/ with --delete, and the repo's copy of that directory is a 2026-10-28 lineage while the live tree carries files it does not (engine4b.py, clones.py, pro_voices.py, seamless.py, limits.py, and the vendored homograph/ package). Run as-is it would delete 82 files from a live service. Stage the homograph package with build_deploy.py; do not use deploy.sh to ship this feature.
